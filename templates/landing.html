03 · Fee reconciliation

Fatima was being chased for fees a scholarship had already paid.

Fatima Khan (23CSE003) had an EWS concession disbursed against her outstanding fees — and a reminder still going out for the same amount. The agent reconciles disbursements against the fee ledger and recommends suppressing the reminder, quoting the platform's own rule back as evidence, with a human approving the call.

"Reminders MUST be suppressed where a sanctioned scholarship or approved installment plan covers the dues. This is the most common cause of avoidable distress in fee follow-up." — comment in the platform schema, finance.reminder_dispatch
Fee Reconciliation → ₹40,000 covered vs ₹40,000 outstanding → suppress, on approval.

How it works with the other 72 agents.

Every team builds one agent, and all of them share a single database. That is the whole trick to integration: our agent never calls anyone else's code. It simply reads the same tables that Agents 10 and 11 fill in, and writes to the tables that Agents 40, 41 and 43 read. Point every agent at the same database and they work together automatically.

1

One shared database, no custom APIs

All 72 agents read and write the same tables. Integration is agents sharing data, not code calling code — so nothing breaks when another team ships their agent.

2

We read what Agents 10 & 11 produce

Marks and attendance land in shared tables. Agent 42 just reads them. Swap our stub for the real agents and nothing on our side changes.

3

We write what Agents 40, 41 & 43 use

Our fee, reminder and loan updates go into tables those agents already watch, so they pick them up on their own.

See it for yourself — don't take our word for it. Sign in and open the Integrations tab: it shows the Google Cloud SQL connection with a live server clock that changes each time you press Refresh, the exact shared tables, and their live row counts.

How it works

Agentic where it counts, deterministic where it matters.

◆

Every number comes from SQL

The engine reasons deterministically over the shared Postgres schema. The LLM only phrases answers — it never invents a figure.

⛓

Full audit trail

Each action writes a run, its inputs, its outputs and a reasoning summary — the evidence an accreditation audit can walk back through.

⚑

Risk flags on renewals

Awards drifting below a renewal rule raise a SCHOLARSHIP_RISK flag with a suggested first action, before the award lapses.

✓

Human-in-the-loop

Anything that touches a student — suppressing a reminder, sanctioning — waits on a human approval gate. The agent recommends; a person decides.

◇

Offline-safe

Runs fully without an API key or internet. Gemini is optional polish on the chat; the system stands on its own.

▤

Lawful use of category

Social category is used only where a statutory scholarship rule requires it — never as a machine-learning feature. The schema forbids the latter.
